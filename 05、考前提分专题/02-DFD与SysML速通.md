# DFD 与 SysML 速通（概念 + 考法 + 答题模板）

> 这两个东西在考试里出现的位置完全不同：**DFD 是案例题的常客**（几乎每隔一两年就有一道"补全数据流图/找错误"），**SysML 是 2023 年才冒出来的新面孔**（考需求图与用例图的区别）。下面按"是什么 → 怎么画 → 考试怎么问 → 怎么答"的顺序讲。

---

# 第一部分：DFD（Data Flow Diagram，数据流图）

## 1. 一句话定义

DFD 是**结构化分析方法（SA）**的核心模型，用图形描述"数据在系统里从哪来、经过哪些加工、存到哪里、最后到哪去"。它只关心**数据流**，不关心控制流、不关心时序。

## 2. 四个元素（必须背到能画）

| 元素 | 画法（教材常见） | 含义 | 命名规则 |
|---|---|---|---|
| 外部实体 | 矩形 | 系统之外、与系统有数据交换的人/组织/系统 | 名词（客户、银行、供应商） |
| 加工（处理） | 圆或圆角矩形 | 对数据做变换的动作 | **动词 + 名词**（"计算运费""校验订单"） |
| 数据流 | 带箭头的线 | 流动中的数据 | 名词（"订单""对账单"） |
| 数据存储 | 两条平行线 / 开口矩形 | 静止的数据 | 名词（"订单表""客户档案"） |

三条铁律：
1. **外部实体之间不能直接有数据流**（必须经过加工）；
2. **外部实体与数据存储之间不能直接有数据流**（必须经过加工）；
3. 数据流必须**有名字**，且方向要与实际业务一致。

## 3. 分层：顶层图 → 0 层 → 1 层

- **顶层图（上下文图）**：整个系统画成**一个加工**，外面一圈外部实体，标出系统的输入输出。
- **0 层图**：把顶层那个加工拆成几个主要子加工（如"订单处理""库存管理""结算"）。
- **1 层图**：再把 0 层里的某个加工继续拆。
- **父子平衡**：子图的输入输出数据流，必须与父图中对应加工的输入输出**完全一致**（名称、数量、方向）。这是案例题最爱考的点。

## 4. 画图五步

1. 找**外部实体**，划清系统边界；
2. 画**顶层图**：一个加工 + 所有外部实体 + 输入输出流；
3. **自顶向下分解**：每个加工拆成 2–5 个子加工（别一次拆太细）；
4. **命名与编号**：加工 P1、P2…，数据存储 D1、D2…，数据流写名词；
5. **平衡检查 + 写数据字典**。

## 5. 案例题最爱考的六类错误

| 错误类型 | 表现 | 怎么答 |
|---|---|---|
| **黑洞** | 只有输入、没有输出 | "加工 Px 缺少输出数据流" |
| **灰洞** | 输入不足以产生该输出 | "Px 的输入缺少 xx 数据，无法生成 yy" |
| **奇迹** | 没有输入却有输出 | "Px 无输入数据流" |
| **非法连接** | 实体↔实体、实体↔存储 直接连线 | "外部实体与数据存储之间不能直接传数据" |
| **父子不平衡** | 子图多出/少了父图的数据流 | "子图缺少/多出 xx 流，与父图不平衡" |
| **命名/方向错** | "处理数据"这种动宾不清、箭头反向 | "数据流命名不规范/方向相反" |

## 6. DFD 与系统流程图、ER 图、数据字典的关系

- **DFD vs 系统流程图**：DFD 画**数据流**、可并行、不强调时序；流程图（系统流程图）画**控制流/处理步骤**、强调先后顺序。2009 年、2019 年案例都直接问过这个区别。
- **DFD vs ER 图**：DFD 是**功能模型**（系统做什么），ER 图是**数据模型**（数据长什么样），两者要交叉校验（2014 年用 CRUD 矩阵校验）。
- **DFD + 数据字典**：DFD 只画结构，**数据字典**定义每个数据流/数据项/数据存储/加工的精确含义，二者缺一不可。

## 7. 真题里怎么出现的（近十五年）

| 年份 | 题 | 考法 |
|---|---|---|
| 2009 | 商业情报处理系统 | 流程图 vs DFD、找 DFD 错误、画 0 层图、高质量 DFD 三原则 |
| 2014 | 库存管理系统 | 找 DFD 错误（黑洞/灰洞）、CRUD 矩阵填空 |
| 2019 | 在线订餐系统 | 补外部实体 E1–E4、补加工 P1–P4、补 4 条数据流 |
| 2022 | 煤矿安全预警 | 补 (1)–(6) 数据流、数据平衡原则、DFD 与数据字典作用 |
| 2026 上 | 在线学习系统 | 数据流图填空 + 推荐冷启动 + 知识图谱 |

## 8. 答题模板（背这一段就够）

> ① **先定边界**：外部实体是……，系统负责……；
> ② **再补缺失**：图中缺少"xx→yy"的数据流，缺少加工"……"；
> ③ **说清原则**：数据流必须命名、父子图必须平衡、每个加工必须有输入并有输出（不能有黑洞/灰洞/奇迹）、实体与存储之间必须经加工。

# 第二部分：SysML（Systems Modeling Language）

## 1. 一句话定义

SysML 是 **OMG 在 UML 2 基础上为"系统工程"扩展出来的建模语言**。UML 主要描述软件，SysML 要描述**整个系统**：硬件、软件、人员、数据、接口、需求、参数约束。

它删掉了 UML 里偏软件的细节，加了四样东西：**需求图、参数图、块（Block）、分配关系**。

## 2. SysML 的九种图

| 图 | 回答什么问题 | 备注 |
|---|---|---|
| **需求图**（Requirement Diagram） | 系统要满足哪些需求，需求之间什么关系，谁满足它 | **SysML 独有，考试重点** |
| **块定义图**（BDD） | 系统由哪些块组成，块之间什么关系 | 相当于 UML 的类图 |
| **内部块图**（IBD） | 块内部各部件怎么连、通过什么端口 | 相当于"装配图" |
| **参数图**（Parametric Diagram） | 性能/约束方程怎么绑定到属性上 | SysML 独有，考得少 |
| 活动图 | 行为与流程 | 同 UML |
| 序列图 | 对象间消息时序 | 同 UML |
| 状态机图 | 状态与迁移 | 同 UML |
| 用例图 | 参与者与系统功能 | 同 UML |
| 包图 | 模型的组织结构 | 同 UML |

记忆口诀：**"需求、块、内块、参数"是 SysML 四件套，其余照搬 UML。**

## 3. 需求图：元素与七种关系（2023 年就考这个）

**元素**：需求（Requirement，通常写成 `id + 需求文本`）、块（Block）、测试用例（TestCase）。

**七种关系**（记住"包、派、细、满、验、复、追"）：

| 关系 | 符号/关键字 | 含义 | 例子 |
|---|---|---|---|
| 包含 Containment | `«contain»` | 复合需求由子需求组成 | "支付系统"包含"支付安全" |
| 派生 Derive | `«derive»` | 由上层需求推导出的新需求 | 由"响应≤1s"派生出"缓存命中率≥90%" |
| 细化 Refine | `«refine»` | 对需求做更细的描述 | 用用例细化"支持在线支付" |
| 满足 Satisfy | `«satisfy»` | 设计元素（块）满足某需求 | "订单服务"满足"下单需求" |
| 验证 Verify | `«verify»` | 测试用例验证某需求 | "TC-01"验证"1s 内响应" |
| 复制 Copy | `«copy»` | 复用另一处的需求文本 | 引用法规条款 |
| 追溯 Trace | `«trace»` | 建立弱关联（如需求↔设计文档） | "需求 R1"追溯"设计说明书 3.2" |

答题时的方向：**块 →（satisfy）→ 需求；测试用例 →（verify）→ 需求**。

## 4. SysML 需求图 vs UML 用例图（2023 年原题就问区别）

| 维度 | UML 用例图 | SysML 需求图 |
|---|---|---|
| 建模对象 | 参与者与系统**功能** | **需求条目**及其关系 |
| 视角 | 用户视角、黑盒 | 工程视角、可追溯到设计与测试 |
| 核心元素 | 参与者、用例、系统边界 | 需求、块、测试用例 |
| 能回答 | "系统给谁做什么" | "需求是什么、谁满足、谁验证、如何派生" |
| 关系 | 包含/扩展/泛化 | 包含/派生/细化/满足/验证/复制/追溯 |

一句话：**用例图回答"做什么"，需求图回答"要求什么、谁来满足、怎么证明满足"。**

## 5. 2023 年案例原题长什么样（记住题型）

> 试题二：软件系统设计与建模
> 问题 1：SysML 需求图与 UML 用例图的定义及区别；
> 问题 2：需求图的七种关系，以及混合动力 SUV 需求图填空；
> 问题 3：用例图填空。

也就是说，**SysML 在案例里目前只考"需求图 + 概念辨析"**，不考参数图、不考 IBD 细节。备考投入产出比很高：把七种关系和与用例图的区别背熟即可。

## 6. 如果考"画需求图/填空"的三步

1. **先列需求条目**：把题干里的"必须/应/不得/在 X 秒内"逐条抽成需求，编号 R1、R2…；
2. **判关系**：上下位 → 包含；从上一条推出 → 派生；换种说法更细 → 细化；落到具体模块 → 满足；落到测试 → 验证；只是引用 → 复制/追溯；
3. **标方向**：`块 --«satisfy»--> 需求`，`测试 --«verify»--> 需求`，别画反。

# 第三部分：一页速查

| 问题 | DFD | SysML |
|---|---|---|
| 属于哪种方法 | 结构化分析（SA） | 系统工程建模（MBSE） |
| 核心元素 | 外部实体、加工、数据流、数据存储 | 需求、块、端口、约束参数 |
| 最常考 | 补全/找错/父子平衡 | 需求图七关系、与用例图区别 |
| 一句话考点 | "数据怎么流" | "需求怎么被满足和验证" |
| 答题关键词 | 平衡、黑洞、灰洞、命名、边界 | satisfy、verify、derive、refine、contain |

## 附：两者与论文的关系

- 论文题若考"建模方法"（2009、2017、2023 都考过），DFD / UML / SysML 可以作为"三种建模方法"的对比素材：**结构化（DFD+数据字典）→ 面向对象（UML）→ 系统工程（SysML）**，正好是一条"从软件到系统"的演进线。
