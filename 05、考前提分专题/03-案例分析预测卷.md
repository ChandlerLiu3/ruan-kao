# 案例分析预测卷（面向 2027 上半年）

> **命题依据**：2023–2026 五次考试的案例走向（质量属性必答 + 缓存 + 建模 + 云边 + AI/IoT），题目按"真题的提问方式"编写，不是押原题，而是押**题型与考点组合**。
>
> **考试规则**：5 道题，第 1 题必答，第 2–5 题选答 2 道，每题 25 分，共 75 分，时间 90 分钟。
>
> **用法**：先闭卷 90 分钟写完，再对照后面的参考答案与评分点。建议每题控制在 25–28 分钟，必答题先做。

## 试题一（必答）政务大模型问答平台的质量属性与架构风格

**【说明】**

某市大数据局建设"政务智能问答平台"，面向市民提供政策咨询，后台采用"知识库 + 大模型"的检索增强生成（RAG）方案。市民在小程序提问，系统先检索政策库，再把检索结果交给大模型生成答案并注明出处。

项目组在需求分析阶段列出如下需求：

- (a) 高峰期 95% 的请求应在 3 秒内返回答案； - 性能、可用性
- (b) 向量检索服务故障时，自动降级为关键词检索，保证仍能回答； - 可用性
- (c) 市民提问内容与回答需加密存储，且每条回答必须能追溯到原文条款； - 安全性 易用性 可测试性
- (d) 新增一个委办局的知识库，接入工作量不超过 2 人天； - 可修改性
- (e) 支持按 10% 灰度用户切换新版本模型；- 可修改性
- (f) 每次发版前须通过 500 条评测集，答案准确率不低于 85%；- 可测试性
- (g) 单次问答的算力成本不超过 0.02 元； - 性能
- (h) 系统能承受日常流量 3 倍的突发访问； - 性能 可用性
- (i) 运维人员可在 30 分钟内定位任一失败请求的全链路；- 可测试性
- (j) 支持小程序、网页、政务大厅自助机三种终端； - 易用性
- (k) 机房断电后 5 分钟内恢复服务。 - 可用性、安全性

架构师提出两种候选风格：
- 方案一：**管道-过滤器**，把"敏感词过滤 → 意图识别 → 检索 → 重排 → 生成 → 合规校验"串成处理链；
- 方案二：**事件驱动（隐式调用）**，各环节通过消息总线发布/订阅事件，异步协作。

**【问题 1】（10 分）** 请将 (a)–(k) 归类到对应的质量属性（性能、可用性、安全性、可修改性、可测试性、易用性），每个属性至少一条。

**【问题 2】（8 分）** 请从**处理顺序可控性、扩展方式、时延、故障隔离**四个维度比较两种风格，并指出本项目应采用哪种（或如何组合），说明理由。

**【问题 3】（7 分）** 针对"检索 + 生成"这条链路，各指出一个**敏感点**和一个**权衡点**，并说明理由。

## 试题一

**【问题 1】质量属性归类（10 分，每条 1 分，归类错不给分）**

| 需求 | 属性 | 说明 |
|---|---|---|
| (a) 95% 请求 3 秒内 | 性能 | 响应时间指标 |
| (g) 单次成本 ≤0.02 元 | 性能（经济性） | 资源效率 |
| (h) 承受 3 倍突发 | 性能（可伸缩） | 容量 |
| (b) 检索故障降级 | 可用性 | 故障转移/降级 |
| (k) 断电 5 分钟恢复 | 可用性 | 恢复时间 |
| (c) 加密存储 + 可溯源 | 安全性 | 机密性 + 审计 |
| (d) 新知识库 ≤2 人天 | 可修改性 | 可扩展 |
| (e) 灰度切换模型 | 可修改性（可测试性） | 灰度发布 |
| (f) 评测集 85% | 可测试性 | 可验证 |
| (i) 30 分钟定位失败请求 | 可测试性（可运维） | 可观测性 |
| (j) 三种终端 | 易用性 | 多端适配 |


- (a) 高峰期 95% 的请求应在 3 秒内返回答案； - 性能、可用性
- (b) 向量检索服务故障时，自动降级为关键词检索，保证仍能回答； - 可用性
- (c) 市民提问内容与回答需加密存储，且每条回答必须能追溯到原文条款； - 安全性 易用性 可测试性
- (d) 新增一个委办局的知识库，接入工作量不超过 2 人天； - 可修改性
- (e) 支持按 10% 灰度用户切换新版本模型；- 可修改性
- (f) 每次发版前须通过 500 条评测集，答案准确率不低于 85%；- 可测试性
- (g) 单次问答的算力成本不超过 0.02 元； - 性能
- (h) 系统能承受日常流量 3 倍的突发访问； - 性能 可用性
- (i) 运维人员可在 30 分钟内定位任一失败请求的全链路；- 可测试性
- (j) 支持小程序、网页、政务大厅自助机三种终端； - 易用性
- (k) 机房断电后 5 分钟内恢复服务。 - 可用性、安全性

**【问题 2】风格比较（8 分，每维度 1.5 分 + 结论 2 分）**

| 维度 | 管道-过滤器 | 事件驱动 |
|---|---|---|
| 处理顺序可控性 | 强，链路固定、顺序明确 | 弱，由事件触发，顺序不保证 |
| 扩展方式 | 加过滤器，需改管道编排 | 加订阅者，松耦合、易扩展 |
| 时延 | 链路串行，时延可预测 | 异步，吞吐高但尾延迟不确定 |
| 故障隔离 | 过滤器故障会阻塞整条管道 | 单订阅者故障不影响其他 |

**结论（参考答案）**：**主链路用管道-过滤器，旁路用事件驱动**。RAG 的"过滤→检索→重排→生成→合规"有严格先后与可解释性要求，适合管道；而审计日志、计费埋点、内容安全异步检测属于"可旁路"的动作，用事件发布解耦，避免拖慢主链路。这也是真题里反复出现的"混合风格"答法。

**【问题 3】敏感点与权衡点（7 分）**

- 敏感点：**检索返回的 Top-K 数量**（或缓存 TTL）。K 越大召回越高但时延与 Token 成本上升，是影响"性能"这一个质量属性的关键参数。
- 权衡点：**模型规模/精度档位**。换更大模型能提升准确率（性能中的"正确性"），但时延、成本、显存同时恶化，同时影响"性能"和"成本/可修改性"多个属性——影响多个质量属性且对多个属性都敏感的，就是权衡点。

## 试题二

**【问题 1】四层架构（9 分，每层 2 分 + 1 分结构）**

| 层 | 职责 | 典型组件 |
|---|---|---|
| 设备层 | 采集与执行：电压电流温度、启停控制 | 充电桩、电表、传感器、PLC |
| 边缘层 | 本地自治：协议转换、本地计费、断网续传、规则联动 | 站控网关、边缘计算节点、本地数据库、MQTT Broker |
| 云平台层 | 设备接入与管理、订单计费、对账、远程运维、数据分析 | IoT 接入网关、设备影子、订单服务、计费服务、时序数据库 |
| 应用层 | 面向用户与运营的业务界面 | 用户小程序、运营后台、运维 App、开放 API |

**【问题 2】QoS 选择（8 分）**

① 电压电流温度 → **QoS 0**：高频、可丢、丢一条不影响业务，追求低开销。
② 启动充电指令 → **QoS 1**：必须送达，允许极小概率重复（指令带幂等 ID 去重）。
③ 结算账单 → **QoS 2**：恰好一次，金额数据不能重复也不能丢。

**【问题 3】断网 2 小时的方案（8 分）**

- **本地自治**：边缘网关保存设备白名单与费率，断网时充电正常进行；订单与电量在本地落库（SQLite/时序库），生成全局唯一订单号（网关 ID + 时间戳 + 序列）。
- **续传**：恢复后按"先补订单、再补流水、最后对账"的顺序批量上传，带幂等键，服务端去重；采用指数退避重试。
- **一致性**：以"本地流水为准、云端做校验"，用对账任务比对电量与金额，差异进人工工单；关键状态（开始/结束）用状态机 + 版本号防覆盖。

## 试题三

**【问题 1】三类缓存问题（9 分，每类 3 分）**

| 问题 | 含义 | 措施（各两种） |
|---|---|---|
| 穿透 | 查询**不存在**的数据，请求直达数据库 | 布隆过滤器拦截；空值缓存（短 TTL）；接口参数校验 |
| 击穿 | **热点 key 过期瞬间**大量并发打到数据库 | 互斥锁重建；逻辑过期 + 异步重建；热点永不过期 |
| 雪崩 | **大量 key 同时过期**或缓存集群故障 | 过期时间加随机抖动；多级缓存；熔断降级、集群高可用 |

**【问题 2】互斥锁 vs 逻辑过期（8 分）**

- 互斥锁：缓存失效时只放一个线程去查库重建，其余线程等待/重试。**优点**：数据一致、实现简单；**缺点**：等待线程阻塞，热点 key 上会有排队，吞吐下降。
- 逻辑过期：value 里存过期时间，物理上不过期；发现逻辑过期后，一个线程异步重建，其余线程**先返回旧值**。**优点**：不阻塞、可用性高；**缺点**：会读到短时旧数据。
- **按"高可用优先"选逻辑过期**：秒杀场景宁可短暂读到旧库存展示，也不能把请求堵死；最终一致性由"库存扣减在 Redis 原子操作 + 异步落库 + 对账"保证。

**【问题 3】防超卖（8 分，答三种即可）**

1. **数据库悲观锁**：`SELECT ... FOR UPDATE` 锁行，简单可靠，但并发低、易锁等待——适合库存少、并发不极端的场景。
2. **乐观锁**：`UPDATE stock SET num=num-1 WHERE id=? AND num>0` 或版本号 CAS，无锁等待，失败重试——适合冲突不高的场景。
3. **Redis 原子扣减**：Lua 脚本 `if stock>0 then decr`，把判断与扣减合成原子操作，配合异步下单与对账——适合秒杀级并发。
4. （补充）**分段库存/令牌桶**：把库存拆成 N 份放到不同 key，进一步削峰。

## 试题四

**【问题 1】实体/加工/存储（8 分）**

- 外部实体：用户、团长、供应商、支付平台、网格仓（可作为内部实体处理）。
- 主要加工：下单、支付处理、拼团汇总、采购下单、入库分拣、配送调度、自提核销、结算分账、退款。
- 数据存储：用户表、商品表、订单表、团点（团长）表、库存表、配送单表。

**【问题 2】五类错误举例（9 分）**

| 错误 | 表现（结合本题） |
|---|---|
| 黑洞 | "结算分账"只有订单输入，没有任何输出（分账结果/账单） |
| 灰洞 | "采购下单"只有商品信息输入，没有库存与供应商数据，却输出采购单 |
| 奇迹 | "生成配送单"没有任何输入，却输出配送单 |
| 非法连接 | 用户（外部实体）直接连到"订单表"（数据存储） |
| 父子不平衡 | 0 层图中"支付处理"有"退款请求"输入，1 层子图里没有 |

**【问题 3】数据平衡与数据字典（8 分）**

- 数据平衡：**父图中某加工的输入/输出数据流，必须与它分解后的子图的输入/输出完全一致**（名称、数量、方向），否则就是父子不平衡；分解可以加内部数据流，但**不能改变对外接口**。
- 数据字典：DFD 只给结构，数据字典给出每个数据流/数据项/数据存储/加工的**精确定义**（组成、类型、长度、取值范围、加工逻辑），两者配合才能完整描述需求；数据字典与 DFD 必须同步维护。

**【问题 1】需求图 vs 用例图（8 分，三点各 2 分 + 总结 2 分）**

① 派生（derive）　② 满足（satisfy）　③ 细化（refine）　④ 验证（verify）　⑤ 包含（contain）　⑥ 复制（copy）　⑦ 追溯（trace）

**【问题 3】箭头方向（8 分）**

- `调度平台 --«satisfy»--> R1`：**由设计元素指向需求**。

# 附：90 分钟怎么分配

| 时间 | 动作 |
|---|---|
