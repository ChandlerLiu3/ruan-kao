## 二、问题 1：四层架构（4.5/9）

### 你的答案

1. 站控网关：边侧鉴权、充电、离线计费、账单上报
2. 云端 API 网关：API 接入、访问控制、BFF
3. 业务层：应用逻辑层，唯一可访问数据的层
4. 数据存储层：查询与落盘，SQL 数据库

### 得分点

- 站控网关的职责抓得准：**本地鉴权 + 离线计费 + 账单上报**，这是边缘层最核心的三件事（+2）；
- 云端有接入层意识（API 网关），业务层/数据层分层正确（+2）；
- 「业务层唯一可访问数据层」这个约束说得对（+0.5）。

### 失分点

1. **少了设备层**（充电桩、电表、传感器、PLC）。题面明确"场站有 20–60 台充电桩"，四层的第一层就该是设备层——它负责采集与执行，是云边协同的起点（−2）。
2. **少了应用层**（用户小程序、运营后台、运维 App）。云端分层不能只到数据层，业务最终要落到"谁在用"（−2）。
3. **两个维度混在一起**：1 是"边"，2–4 是"云的纵切"。四层应是 **设备层 → 边缘层 → 云平台层 → 应用层**，是横着切的四个平面，不是"边缘 + 云端三层"。
4. API 网关、BFF 是**组件**，不是"层"；BFF 属于接入层的一种实现，放在"云平台层"里讲更稳。

### 参考版

| 层 | 职责 | 组件 |
|---|---|---|
| 设备层 | 采集与执行：电压/电流/温度、启停控制 | 充电桩、电表、传感器、PLC |
| 边缘层 | 本地自治：协议转换、本地鉴权与计费、断网续传、规则联动 | 站控网关、边缘节点、本地库、本地 MQTT Broker |
| 云平台层 | 设备接入与管理、订单计费、对账、远程运维、数据分析 | IoT 接入网关、设备影子、订单/计费服务、时序数据库 |
| 应用层 | 面向用户与运营的业务界面 | 用户小程序、运营后台、运维 App、开放 API |

## 三、问题 2：MQTT QoS（6/8）

### 你的答案与判定

| 项 | 你的答案 | 判定 |
|---|---|---|
| ① 电压电流温度 | QoS 0 | ✅ 正确，理由也对（可丢、不影响业务） |
| ② 启动充电指令 | QoS 2 | ⚠️ 方向对（要可靠），但选择偏重，标准答案是 QoS 1 |
| ③ 结算账单 | QoS 1 | ❌ 偏低，账单要 QoS 2 |

### 关键纠偏

MQTT 三档的本质是**投递语义**：

- **QoS 0**：至多一次，发完不管，可能丢。适合**高频、可丢**的遥测。
- **QoS 1**：至少一次，可能**重复**。适合**不能丢、但重复可容忍**的消息。
- **QoS 2**：恰好一次，四次握手，开销最大。适合**既不能丢、也不能重**的消息。

按这个标准重排：

- 遥测 → **0**（丢一条无所谓，省带宽）；
- 启动/停止指令 → **1**（不能丢；重复由"指令幂等 ID + 状态机"消掉，比 QoS 2 更实时、更省）；
- 结算账单 → **2**（重复就意味着**重复扣费**，这是钱的问题，必须恰好一次）。

你现在的写法正好**把 ② 和 ③ 对调了**。记住一句话：**"钱用 2，控制用 1，遥测用 0"**。

补充：说 QoS 1 时一定要带一句"服务端按消息 ID 去重"，否则会被追问"重复怎么办"。

## 四、问题 3：断网 2 小时（4.5/8）

### 你的答案

- 站控网关具备用户数据，扫码后可用离线数据提供充电服务；
- 网络恢复后上传消费数据和日志，进行数据补登。

### 得分点

- 抓住了"边缘自治"：本地有用户数据 → 断网也能鉴权开充（+2）；
- 抓住了"恢复后补传"这个大方向（+2）；
- 方向没跑偏，扣分主要在**深度**。

### 失分点

1. **没有"本地落库"**：断网期间的订单、电量、金额必须先在网关本地持久化（SQLite / 时序库），只靠"上传日志"不够，日志不是账（−1）。
2. **没有幂等**：补传会重试，服务端必须按"网关 ID + 序列号/订单号"去重，否则会重复计费（−1）。
3. **没有对账**：补传不等于一致，要有一致性手段——本地流水为准、云端校验、差异进工单（−1）。
4. **没提计费规则本地化**：费率、免费时长、分时电价要下发到边缘并缓存，断网时才能算钱（−0.5）。

### 参考版（四段式，直接背）

1. **本地自治**：网关缓存用户白名单、费率与设备档案；断网时本地完成鉴权、启停与计费，订单落本地库，生成全局唯一订单号（网关 ID + 时间戳 + 序列）。
2. **本地持久化**：订单、电量流水、金额分表存本地；用 WAL 保证断电不丢。
3. **恢复补传**：按"先订单、再流水、后状态"的顺序批量上传，带幂等键，指数退避重试；服务端去重后入账。
4. **一致性兜底**：定时对账（本地流水 vs 云端账单），差异自动挂起 + 人工工单；关键状态用状态机 + 版本号防覆盖；时钟以云端为准做校准。

## 五、下次练习的重点

1. **架构分层题先画横切面**：设备 / 边缘 / 云 / 应用，四层各自"职责 + 组件"两列写，别把组件当层。
2. **QoS、一致性这类"语义题"要背判定口诀**：钱用 2、控制用 1、遥测用 0；至少一次要配幂等，恰好一次要配去重。
3. **"断网/弱网"题按四段答**：本地自治 → 本地持久化 → 恢复补传 → 对账兜底。这四段也适用于 2025 下"餐饮云-端协同"和 2026 上"AIoT 云边协同"。
4. 目标：**每道选做题至少写满 6 个要点、3 个小标题**，让阅卷人一眼看到结构。
